# Supabase user-token verifier — isolated implementation, 2026-09-14

The optional createSupabaseHypothesisAuthenticator adapter uses the existing installed Supabase SDK auth.getUser(jwt). Configuration is absent by default. It requires an exact HTTPS project origin, matching Auth issuer, explicit audience and a publishable-key format. Secret/service-role/legacy JWT keys are rejected; no new key or endpoint is configured.

The adapter restricts its SDK fetch to one GET at the pinned /auth/v1/user endpoint for each attempt, with the supplied user token and publishable key. No cookies, redirects, persistent Auth session, automatic token refresh, caller-controlled URL or response cache is used. Responses are bounded to64KiB; the operational deadline is configurable up to30seconds (10seconds default). These are transport limits, not semantic thresholds or production identity lifetimes.

Unverified token claims are used only to reject wrong scope, expired/future, anonymous, non-user or malformed credentials and to bind the subsequent authenticated response. They never establish identity by themselves. The SDK Auth request must succeed; returned UUID/audience/role/non-anonymous state must match. Metadata is stripped and the handler receives only id and is_anonymous:false. Current database membership/permission checks remain authoritative for operations.

Tests use a separate ephemeral RSA key and an in-process signed synthetic Auth provider. They exercise rejected claims, wrong signing key, a simulated provider revocation, response substitution, malformed/oversized/redirect/error responses, deadline and no repeat network request. The configured native client/handler/store/worker test now uses this actual adapter/SDK and synthetic provider instead of a Bearer-string success callback. Invalid and provider-denied requests must not query PostgreSQL. No real project, user token, signing key, source or provider endpoint is used.

This is not deployment or real Supabase provider qualification. In particular, the simulated provider revocation is not proof that a production logout invalidates an already issued JWT immediately. Production session-revocation semantics, clock behavior, endpoint/issuer/audience and intended-host custody must be checked in the separately approved trial. Legacy token formats that lack the required claims remain closed pending explicit compatibility evidence. No service_role credential enters the worker or verifier.

Primary references: [Supabase getUser](https://supabase.com/docs/reference/javascript/auth-getuser) documents the Auth-server request and explicit JWT argument; [API keys](https://supabase.com/docs/guides/getting-started/api-keys) distinguishes low-privilege publishable keys from elevated secret/service_role keys. These sources establish the API contract, not authorization to use a live project.
