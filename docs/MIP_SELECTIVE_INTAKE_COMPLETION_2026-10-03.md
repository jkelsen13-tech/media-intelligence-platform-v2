The `capture` action accepts either the original delivered article or a guarded
retained continuation. Each continuation delegates to an existing native owner
inside the same SQL transaction as current reviewer, rights/expiry/revocation,
registered criteria/policy, source endpoint, discovery head, execution head,
retained capture and native workspace-head checks. Initial completion also checks
the runner's deterministic observation/version IDs in SQL. Changing a caller's
expected head cannot bypass a competing native version.

A known committed capture can therefore resume candidate, assessment,
observation, version and annotation progress without a source request. Native
idempotency preserves the original capture/candidate, exact content hash/span,
assessment and receipt identities after lost responses. Pending progress with
stale analysis, conflicting receipts, changed scope/head, superseded selection,
expired analysis rights or revoked terms fails closed and retains private history.
Annotation rechecks native current assessment causes and supersession; it also
uses the existing source/version advisory-lock namespaces before freshness checks.
These single-session tests do not establish independent-connection race proof.

A consumed permit is never reopened. A failed fetch, expired delivery permit or
rolled-back native capture cannot automatically reacquire. Only an explicit
separately authorized successor selection with the exact discovery predecessor
may obtain a new permit within the existing grant quota. Reusing a capture permit
with different canonical source bytes rejects before another native job is created.
The existing streamed HTTP byte/deadline budget and the SQL serialized-payload
budget both remain conservative bounds.

explicit reconciliation through the existing native owners. The sequence remains
