# Private investigation Following source binding — 2026-10-02

This candidate binds the retained private Following foundation to the existing assigned-investigation consumer. It is a partial private preference capability, not the accepted public Story Following product. No SQL was applied and no gateway or frontend was deployed. Trusted reviewer material declarations remain provisional and unexposed in the consumer API. Architecture review and integration remain necessary before activation.

## Existing owners and exact binding

`mipBackend.investigations` already composes the installed Supabase SDK through `createInvestigationBackend`. The added `following` client uses `functions.invoke('investigation-api/following')`, the current session supplied by that SDK, and the existing gateway's verified Auth boundary. No App, composition root, Auth lifecycle, deployment entry point, public reader, historical migration, SQL proposal, or transport URL changed. The original private Following branch remains frozen.

The gateway reuses `createFollowingHandler` from the original source proposal. It exposes only `list`, `read`, `subscribe`, `acknowledge`, and `unsubscribe`; explicit reviewer material classification and administrative revocation are refused. Its one fixed SQL target is `mip_investigation_following_v1` on the existing validated backend origin, using the existing server credential boundary. Assignment, immutable private version/observation identity, explicit graph subject, event idempotency, cursor CAS, and revocation remain SQL-owned. There is no external notification or in-app delivery service.

Successful private Following responses add `authenticated_user_id` from the server-verified Auth user. A SQL response cannot override it, and request JSON cannot supply it. The optional `X-MIP-Expected-User` header is a refusal precondition: the gateway compares it to verified Auth before invoking SQL and refuses a malformed or different value with fixed `authentication_required`. It never supplies identity or authority. Header-free API calls retain the current verified actor's semantics. The UI supplies its displayed workspace owner as validated, snapshotted client metadata; it is not placed in the JSON input. The client and hook also require matching response actors for reads, mutation receipts, and post-write confirmation. No additional Auth roundtrip or local token parsing was introduced.

## Foreground UI behavior

The minimal existing private workspace mount starts with unknown Following status and reads only when the user chooses Load status. Subscribe/unsubscribe/acknowledge success is displayed only after a matching immutable receipt and one foreground confirmation read. There is no mount query, polling, background notification, automatic mutation retry, or optimistic saved state. A missing/unbound RPC, malformed payload, or exception is unavailable, never a claim that an account is unfollowed.

Acknowledgment binds the exact displayed immutable version and explicit graph subject. The current head may be newer; this does not silently change the displayed version or cursor. Current-head/saved-anchor mismatch is disclosed and prevents acknowledgment. Retained declaration rows must share the subscription's exact subject. Only registered declarations are listed, with provisional materiality and incomplete coverage disclosed; an unclassified version advance remains unknown. Neither an empty page nor a saved preference establishes truth, publication eligibility, complete coverage, or a substantive investigation review.

The hook withholds previous identity/version data immediately on rendering an account/version switch, invalidates pending operations, and discards late reads and writes. Auth expiry and assignment revocation clear the actual existing private workspace via its access-failure owner. A stale cursor clears the local Following payload and asks for an explicit reread; it does not reread or repeat a mutation automatically. Reviewer declarations are not produced by following or acknowledgment.
