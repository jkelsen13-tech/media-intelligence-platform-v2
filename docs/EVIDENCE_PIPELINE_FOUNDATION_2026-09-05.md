## Implemented behavior

- Durable import jobs record pending, processing, retry_wait, completed and dead_letter states. Every processing attempt appends a job event. Run receipts associate reused jobs with each submitting run and retain the original submitted URL.
- Database URL normalization removes fragments and known tracking keys while preserving scheme, path, meaningful query parameters/order and trailing slashes. A normalized URL plus SHA-256 of the normalized payload deduplicates submissions across runs. A unique article identity prevents separate imported copies. Different outlets/URLs carrying similar text are deliberately not merged or declared independent.
- Row locks with SKIP LOCKED reserve one job at a time. UUID lease tokens reject stale workers. Leases expire after two minutes; failures use 30/60/120/240-second backoff, with five attempts maximum. Exhausted jobs remain inspectable in dead_letter. Repeated submissions do not reset the attempt budget.
- Article creation, capture insertion, successful status and completion event commit atomically. A lost HTTP response may leave an indeterminate client result, but never triggers destructive compensation. Rechecking durable state resolves it.
- A new publisher version of an existing URL is retained as a separate pending capture. It never overwrites or inherits approval from the existing article. All new articles use the existing `pending_review` default.
- Exact-source evidence candidates support claims, graph relationships, timeline associations and geographic associations. They refer to captured article content and canonical UUIDs, never IDs invented from labels. Quote offsets are zero-based Unicode code points with an exclusive end, validated against the stored source field in Postgres.
- Geographic candidates must match the event, place and revision in the existing released spatial projection. No direct REFERENCES/SELECT grants on private spatial tables are added. Superseded/unreleased revisions cannot be newly linked through this path; already captured associations remain historical candidates.
- Candidates preserve uncertainty, extractor version and optional predecessor identity. Conflicting reuse of an idempotency key fails. All candidates remain pending; they create no public nodes, edges, timeline events, spatial assertions or publication decisions.
- Append-only history captures article, graph-node and temporal-assessment changes, including reversions and deletion tombstones. Existing records receive installation baselines. Embeddings are excluded because they are recomputable. Baselines do not represent missing past versions.
- The operator can inspect history by record identity and ordinal, or all evidence candidates attached to an event. These reads are private, paginated and source-linked.

## Access boundary

`evidence_pipeline` is a private schema with RLS and no browser policies. `anon` and `authenticated` cannot access its tables/functions or the `public.mip_pipeline_v1` RPC.

The existing `service_role` gains SELECT on articles and INSERT on only these columns: `feed`, `outlet`, `title`, `url`, `summary`, `body_text`, `published_at`, `ingestion_run_id`. It cannot set `reader_state`, `source_status`, claims or other publication fields, and gains no article UPDATE/DELETE permissions. The worker uses SECURITY INVOKER throughout. Its key belongs only in a server environment, never any VITE variable or client bundle.

New private tables explicitly revoke inherited grants before granting the required server access. History tables have UPDATE/DELETE/TRUNCATE rejection triggers. Base article/node/config truncation is also blocked to prevent unrecorded removal. Administrative DDL can still disable triggers; this is application auditability, not tamper-proof storage against the database administrator.

Spatial role memberships, the existing spatial runtime, release policies, public view definition, current article/event/assessment contents, and cron schedules remain unchanged.

## Operator usage

Install dependencies using `npm ci`. No extra subscription or compute tier is needed for these tests.

Create a local JSON manifest:

```json
{
  "run_id": "an-explicit-run-identifier",
  "articles": [{
    "url": "https://publisher.example/report",
    "title": "The actual publisher title",
    "outlet": "The actual publisher",
    "summary": "An accurately retained publisher excerpt",
    "published_at": "2026-09-05T00:00:00Z"
  }]
}
```

This is a shape example only, not a real source to ingest. Inputs must be actual approved records. Optional `body_text` is retained as supplied; this module does not fetch publisher pages or bypass access controls.

```bash
node scripts/evidencePipeline.mjs enqueue manifest.json
# Above is shape validation only, with no connection or writes.
# Set MIP_PIPELINE_URL to the exact v2 URL and MIP_PIPELINE_SERVICE_KEY
# securely in the operator environment before executing a write.
node scripts/evidencePipeline.mjs enqueue manifest.json --apply
node scripts/evidencePipeline.mjs run --apply
node scripts/evidencePipeline.mjs status run.json
node scripts/evidencePipeline.mjs history history.json
node scripts/evidencePipeline.mjs evidence event.json
node scripts/evidencePipeline.mjs candidate candidate.json --apply
```

`run.json`: `{"run_id":"an-explicit-run-identifier"}`.
`history.json`: `{"record_kind":"article","record_key":"article-uuid","after_ordinal":0}`. Kinds also include `graph_node` and `temporal_assessment`; the latter uses the exact pipeline_config key. Pages contain at most 100 versions; continue after the last ordinal.
`event.json`: `{"event_node_id":"canonical-event-uuid"}`. Continue after a page using both `after_time` and `after_id` from its last row.
For a bounded worker run, supply a JSON file containing `{"maxJobs":10}`; maximum 100. It processes available jobs across the queue and exits without waiting for future retries. A future invocation picks up retries when due. No scheduler was enabled.

Candidate input fields are defined in the migration and tested for all four families. A candidate always requires capture ID, candidate key/kind, statement, source field, exact span/excerpt, extractor version and remaining uncertainty. Timeline/relationship/geography records require their canonical target IDs. Submitted `review_state` or unrecognized fields are rejected.

The payload fingerprint is SHA-256 over Postgres `jsonb::text` after normalization. It is an import identity checksum, **not** the spatial runtime's JCS fingerprint or an assessment of evidence quality.

## Recovery and handoff

Routine correction: append a new capture/candidate, or make an authorized administrative edit with `SET LOCAL mip.change_reason = 'specific reason'` in the same transaction; the existing value is preserved in history. Never edit history rows to simulate a correction.

Operational rollback: stop the new operator worker; no cron needs disabling. Keep the private data/history in place. Removing this schema or disabling triggers is a separate administrative removal operation requiring an export of its records first. Do not run `DROP ... CASCADE` to undo it.
