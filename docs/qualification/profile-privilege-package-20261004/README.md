# Profile privilege offline package — 4 October 2026

This is a standalone **offline source package** for the previously qualified, unapplied profile least-privilege proposal. It does not add an installation stage or execute SQL. The compiler has no database client, credential handling, network transport or submission function. Its default output ends with `ROLLBACK`. An explicit `commit` mode produces reviewable source only. File receipts bind bytes and create zero acceptance, rehearsal, COMMIT, recovery or release authority.

The proposal remains exactly 3,870 bytes, SHA256 `2d6f494d51b0aa97be2d74865be99befe802280f3f466fbb95333ba5ec2824f7`, Git blob `a485ecdf0125fa7cd7ff82f1056dc452040deb51`. Its guarded owner-only table revoke removes only TRUNCATE, TRIGGER, REFERENCES and MAINTAIN from `anon` and `authenticated`. PostgreSQL table REFERENCES revocation also removes the corresponding owner-granted column REFERENCES. No GRANT, CASCADE, data write or generic ACL reset is generated.

## Inputs and integrity

`scripts/profilePrivilegePackage.mjs` derives the baseline query from the proposal's exact `BEGIN BASELINE QUERY` / `END BASELINE QUERY` bytes. `scripts/profilePrivilegeCatalog.sql` is a read-only template with one substitution marker. `profileCatalogCaptureSql()` returns a reviewable `BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`, local controls, `SET LOCAL search_path=pg_catalog, pg_temp`, the complete query, and `ROLLBACK`. Catalog capture uses this explicit schema order for relation lookup and decompiler output, and binds the exact context in `identity.search_path`. The raw `profileCatalogQuery()` is suitable inside an already controlled transaction; catalogs from any other context are refused. Collecting any real catalog requires a separately authorized executor; this package includes no collector.

An accepted input document uses contract `mip-profile-privilege-accepted-catalog-v1`, an observation timestamp, qualification `SYNTHETIC_PGLITE_ONLY` or `INDEPENDENT_NATIVE_CATALOG`, the complete `catalog`, and an `acceptance` object. The acceptance object contains `status: INDEPENDENTLY_ACCEPTED`, nonempty `accepted_by`, `accepted_at_utc`, and SHA256 bindings for `catalog_sha256` (`JSON.stringify(catalog)`), `query_sha256` (the expanded query) and `proposal_sha256`. These declarations are evidence inputs for an external acceptance process; the compiler cannot authenticate the reviewer or grant that process authority. Duplicate JSON members, invalid UTF-8, malformed security fields, missing matrices and timestamps outside the five-minute source freshness bound are rejected.

The catalog binds current/session users, table owner, database name/OID, server address/port/version and table OID; relevant role attributes and membership options/grantors; raw baseline ACLs and exploded table/column grants with grantors/options; a complete table/column effective-permission matrix; public/auth schema owners/ACLs; profile rows; RLS/FORCE RLS, column definitions, constraints, policies, and the scoped signup trigger/function definition/owner/ACL. Browser superuser or BYPASSRLS facts are rejected. Effective broad grants through PUBLIC, inherited roles, unexpected grantors, and dependent browser grants require separate diagnosis and are refused.

The additional complete `browser_paths` matrix evaluates each browser against every relevant role using PostgreSQL `pg_has_role(..., 'USAGE')`, `'SET'` and `'MEMBER WITH ADMIN OPTION'`. It binds each role's effective broad table privileges, column REFERENCES, owner access and administration targets. The wrapper refuses switchable/inherited broad or owner access, switchable superuser/BYPASSRLS/CREATEROLE roles, direct/inherited ADMIN privileges and administration available through a switchable role. It permits inert nonadmin memberships with both INHERIT and SET disabled, and benign role switching that retains own-row RLS. This guard covers catalog-declared permitted role switching as well as immediate current-role privileges; it does not claim native concurrency qualification or audit arbitrary privileged functions.

This package requires complete observed profile-row scope. A direct table owner observes all rows when FORCE RLS is false. When FORCE RLS is true, the verified current-owner role must itself have SUPERUSER or BYPASSRLS; otherwise capture sees only that identity's policy-visible rows and the compiler refuses before any privilege change. These PostgreSQL exceptions are described in [PostgreSQL 17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html). The non-super fixture demonstrates zero visible rows under FORCE RLS despite three known fixture rows. No bypass, grant, disable or ownership helper is generated to make such a capture qualify. The static absence of row writes is distinct from observed complete-row readback, and neither fixture claim supplies managed/native proof.

Accepted catalogs, output SQL, integrity receipts and original provenance files must be private regular files (`0600` on this executor). Reads reject symlinks with `O_NOFOLLOW`, compare opened-file identity and metadata, and re-read bindings before publication. The reused unchanged `writeArtifact()` helper reserves both new names exclusively and writes/syncs a private SQL/receipt pair. A collision preserves existing files; incomplete pairs fail verification. The receipt binds the complete existing `launchInstallationSourceIdentities()` closure, including the imported writer and all its declared transitive helpers, plus the profile proposal and the three new source files. A source-binding manifest records the exact qualification source head/tree.

## SQL shape

The compiler inserts its guards inside the proposal's single transaction. It sets **LOCAL** lock timeout 5s, statement timeout 30s, idle-in-transaction timeout 30s and `search_path=pg_catalog, pg_temp` before a bounded `ACCESS EXCLUSIVE` profile relation lock and any catalog query. The same controlled lookup/decompiler context applies to the unchanged historical proposal and to HOLD recovery. It then compares the full fresh accepted security/session/catalog/row baseline, supplies the proposal's expected-catalog GUC locally, runs the unchanged guarded revoke body and compares the resulting catalog to the exact allowed delta. Guard delimiters are selected to be absent from their complete bodies, and interpolated values use explicitly escaped `E` literals; profile/catalog text containing dollar-quote markers, quotes, backslashes or newlines remains exact even with nonstandard string settings. Owner grants to the two browser roles lose only the four table privileges and column REFERENCES, including their grant options. Every surviving exploded ACL entry preserves its privilege, grantor and grant option. Raw column ACLs without removed REFERENCES remain exact; columns with that permitted removal and the table ACL are compared through complete exploded entries. RLS, FORCE RLS, policies, schema ACLs, service privileges, scoped signup function/trigger, unrelated grants and rows must remain exact. Capture, forward and HOLD transaction boundaries restore the prior local context/settings.

These are per-lock/per-statement/idle source controls, **not a total transaction deadline or a qualified native execution budget**. A profile table lock narrows concurrent profile row and relation/catalog races. Native multi-session role/membership/function/session changes and hosted execution, cancellation, drain and connection-loss behavior remain unqualified. The source does not lock all shared role catalogs or serialize the entire service. Do not interpret fixture success as proof of those properties.

## Compile and verify

Use a newly accepted private catalog and a new output path:

```sh
node scripts/compileProfilePrivilegePackage.mjs accepted-private.json new-rehearsal.sql
node scripts/compileProfilePrivilegePackage.mjs accepted-private.json new-rehearsal.sql verify
node scripts/compileProfilePrivilegePackage.mjs accepted-private.json new-commit-source.sql commit
```

`verify` reconstructs the SQL and receipt against the current source and the exact accepted file bytes; it rejects expired observations, changed input/source/original bytes, altered SQL or receipt content and incomplete pairs. These commands do not submit their SQL. There is no live operation mode and no automatic retry.

## Recovery

For a separately authorized rollback-only rehearsal, the original PostgreSQL transaction's `ROLLBACK` restores the initial privileges and rows. Fixture tests observe installed state before executing the actual final ROLLBACK and compare the complete original catalog and session-local settings afterward. A future native operator must obtain **original-channel ROLLBACK acknowledgment** and independently fresh restoration readback. Matching catalog/row values or a local integrity receipt alone cannot establish acknowledgment. Missing acknowledgment remains UNKNOWN and calls for separately authorized read-only reconciliation.

After a future committed installation, this package supports only an exact **HOLD/readback** artifact:

```sh
node scripts/compileProfilePrivilegePackage.mjs fresh-installed-private.json new-hold.sql recovery-hold original-accepted-private.json original-commit-source.sql
node scripts/compileProfilePrivilegePackage.mjs fresh-installed-private.json new-hold.sql verify original-accepted-private.json original-commit-source.sql
```

The HOLD binds the original commit **source artifact** and its integrity receipt, the original accepted baseline, a newer fresh accepted installed catalog and the exact current source closure. The original source receipt is provenance, not proof that any real installation committed. HOLD requires the installed catalog to match precisely the proposal's allowed delta, then reads/verifies that state inside a rollback-only transaction; it performs no restoration grant or data change. Unexpected rows, grantors/options, other deltas, drift and wrong original source mode/bytes are refused.

Restoring browser TRUNCATE/TRIGGER/REFERENCES/MAINTAIN would increase privileges. It needs a separate future exact owner/grantor/grant-option restoration package, independently accepted current facts and explicit security approval. This qualification does not supply such a package or authorize automatic regrant. Preserve populated history and installed state while that decision is pending.
