The connection loop follows [PG17 asynchronous connection polling](https://www.postgresql.org/docs/17/libpq-connect.html): wait for writing first, then respect read/write polling states, fetch the socket again after each poll and use an explicit monotonic application budget. A wakeup without readiness is not permission to poll. Successful connection is checked for exact connection status, server major 17, protocol 3, TLS in use/protocol, pinned host/address/port/user/database, UTF8, nonblocking mode and idle transaction state. These checks do not replace provider identity or qualification evidence.

Each query uses `PQsendQueryParams` with one frozen statement, separately bound private text/NULL parameters and text-format results. BEGIN uncertainty is recorded before attempting submission. There is one connection attempt and no command replay, automatic retry, pipelining or combined deadline/operation submission. Flush waits service both read and write readiness and consume incoming bytes. Successful acknowledgment requires one exact PGresult status, command tag, row count, column names, type OIDs/formats, all consumed results through final NULL and the exact transaction state. Membership tags are `GRANT ROLE`/`REVOKE ROLE`; column tags are `GRANT`/`REVOKE`; the unchanged guarded operation returns `DO` with no rows. The internal DO guard establishes update-one only on successful DO completion. The [PG17 tag table](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/include/tcop/cmdtaglist.h) distinguishes these tags.

Private results preserve SQL NULL as `None`, booleans as exact booleans, integers as checked integers, JSON/JSONB as parsed private values and text as exact text. NULL JSON, missing fields and false/NULL booleans are retained or refused according to the fixed result policy, allowing the host's semantic checks to reject unsupported baselines. Values are copied before `PQclear`; every obtained result is freed, including errors, mismatches and extra results. An extraction limit of 16 MiB applies after libpq has buffered the result; it is not a bound on native buffering or process memory. Private dataclass representations omit values. Raw diagnostic C functions are never bound/read, and a retained no-op notice receiver is installed before polling/query submission to suppress libpq's default NOTICE output. All propagated transport failures contain fixed allowlisted codes only. See [PG17 asynchronous result handling](https://www.postgresql.org/docs/17/libpq-async.html) and [transaction status](https://www.postgresql.org/docs/17/libpq-status.html).

Only `PQcancelCreate`, `PQcancelStart`, `PQcancelPoll`, `PQcancelStatus`, `PQcancelSocket` and `PQcancelFinish` are used for cancellation. The new API inherits the connection's encryption/verification requirements; deprecated plaintext cancellation is unavailable through this component. Cancellation polls use their own application observation budget and fetch the changing cancellation socket each time. Every allocated cancellation connection is finished, including failure and timeout. [PG17 cancellation documentation](https://www.postgresql.org/docs/17/libpq-cancel.html) explicitly separates dispatch from the original command's outcome.

`cancel_and_drain()` attempts original-result drain even when cancellation fails or times out. Its `DrainOutcome` reports cancellation dispatch and original terminal drain separately; drain is not a successful command acknowledgment or proof the command was canceled. Outstanding work, disconnection, unknown/active final transaction state and unsupported COPY/pipeline statuses prevent rollback from being queued behind uncertain work. Final NULL with a usable known state permits only recovery after a failed/mismatched command; it never promotes mismatched/extra/error results to success. Closing frees the connection while retaining outstanding uncertainty, and never proves rollback. Lost rollback acknowledgment, missing independent verification and failed restoration remain UNKNOWN at the host level.

Budgets are finite, positive application observation limits capped at 300 seconds. Event-loop scheduling, C calls, file/crypto work and the server can exceed nominal times; there is no strict wall-time deadline promise. The host must serialize access on one thread, preserve private baselines outside the transaction, enforce each authenticated window/scope/phase and retain explicit recovery/independent-verifier duties. Ordinary Python/native process memory provides no guaranteed zeroization, tamper resistance or secret-custody certification.
