## Exact remaining implementation boundary

A qualifying existing-row operation would have to own all of these together:

1. A read-only extraction/resolution plan before any mutation, bound to a specific authorized article and exact selected capture/record revision, source fields/hash and status. Current legacy selection has only article fields, while native captures, article history revisions and current mutable article bytes are distinct identities.
2. A server transaction that locks the article, revalidates the existing reader/source predicate and exact selected source version, then commits every accepted source normalization, canonical entity/alias/count operation, article-entity change, citation replacement, completion marker and durable receipt together. Approval must serialize against that row/transaction; another independent HTTP eligibility check would recreate the gap.
3. Explicit canonical-entity-resolution authority, including normalization/alias/fuzzy identity decisions and mutation of shared entity records. An article-row grant or citation-only RPC does not confer that separate responsibility. Relevant entity locks/version checks and consistent lock ordering also need a defined contract.
4. A recorded trusted invocation/permission owner for that existing-row operation. The current native service cannot UPDATE or lock the article. A new privileged definer, UPDATE grant, added existing-row action to the old new-URL credential owner, or unauthenticated transaction gateway would introduce a trust boundary that this task does not authorize. No such boundary is selected here.

Holding an article lock in a new helper could technically serialize approval and derived writes, but it is not an existing installed owner, and cannot alone certify what a reviewer read before approval. Exact reviewed-source/version binding and the approval owner's compare-and-set contract remain separate required evidence. This note does not invent a new publication threshold or claim that unrelated public projections become capture-version-bound.

The bounded safe disposition is to preserve the actual native immutable/pending-capture route and keep legacy reactivation gated until that precise operation and entity authority are established. Graph writer role/activation/trigger evidence remains parent-owned and does not affect this permission-preserving diagnosis. No blanket SELECT change or source/backfill edit is warranted by an absent transaction owner.
