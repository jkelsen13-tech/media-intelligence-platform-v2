# Registered native boundary integration v2 — isolated candidate

This candidate adds an actual source-authorized marker issuance, source capture, independently retained delivery, custody-bound permit preparation and native advancement path. It is synthetic qualification only; production admission and a physically independent custodian are not configured.

The original v1 SQL implementation bodies are retained under private names; public incarnation wrappers now reject explicitly registered v2 bindings before delegating legitimate v1 calls. This prevents fallback after publication downgrade. Legitimate v1 contracts remain unchanged. The additive 022 uses separate entrypoints, a registered exact two-table publication contract, per-binding marker filter, and the existing immutable capture/permit/checkpoint chain primitives. Version-two registrations explicitly pin the contract digest. The fixture forwards all incarnation and contract arguments unchanged to source SQL.

The source assigns marker epoch/xid and admits only the currently authorized binding and incarnation. A marker issuance transaction must commit before capture; capture consumes the next published transaction, including preceding revision transactions, without skipping. Marker tuples are matched to the committed source issue. The consumer retains and reads back the complete source transcript and typed delivery, validates the full bootstrap evidence, and advances through current external custody and source authority. All historical_time_qualified fields remain false.

Source and external journal fixtures are separately authenticated capabilities but share the disposable PostgreSQL physical restore domain. This is NOT physical independence. No real source identity, production credentials, deployment or live Supabase changes are authorized by these tests.

Implementation/verification status: initial testable remote increment. Hosted native/golden results must be inspected before freezing. Additional adversarial cases and failures will be retained in GitHub history. The final report must distinguish proven native integration from remaining production custody, provisioning, retention/scheduling and independent audit gates.

Custody assumptions: the admitted journal is append-only and durable, with current readback; the source-scoped custody authority excludes registration replacement and credential revocation across awaited source operations. The consumer revalidates every bootstrap page and its manifest/hash immediately before prepare and again before advance. Preflight alone is not claimed as permanent retention. A backend permitting deletion/corruption during those authority-fenced operations is not an admissible custodian; the disposable fixture does not establish physically independent storage.

Readback checks do not create a distributed transaction. Arbitrary concurrent rollback or disappearance in another store between the final check and native source effect cannot be prevented by these checks alone. Admitted custody must supply durable append-only storage and exclusion for its failure/revocation model; physically independent custody remains a real-activation requirement. Tests include missing and corrupt paged bootstrap evidence after successful prepare and require that advancement is never called.

Native lock-order qualification observes the exact active outer custody transaction PID as the revocation blocker while the inner source gateway transaction is held. PostgreSQL may wait on that earlier shared authority holder first. The source commit gate, exact source receipt readback, and reverse-order zero-checkpoint denial remain mandatory; an arbitrary waiting connection is not evidence.
