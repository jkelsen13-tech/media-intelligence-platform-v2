## Disclosed sandbox accommodation

This sandbox blackholes `tile.openstreetmap.org`: connections hang beyond
150 s without ever erroring. Stock Cesium holds globe tiles non-renderable
while imagery requests hang, so no build of the app can draw the globe here
while OSM hangs. OSM requests were therefore aborted fail-fast (a plain
imagery-outage emulation: tiles render the globe base color plus, where
approved terrain exists, the relief tint). Terrain traffic to AWS was
untouched and real. This accommodation is recorded in the evidence JSON.

## Invisible-globe investigation (correction of the 22-05Z suspicion)

The 22-05Z run suspected the shipped relief material made the globe
invisible. Resolved by minimal-repro matrix and engine-source reading:

- `Material.translucent` is not referenced by globe rendering anywhere in
  `@cesium/engine` 1.145 (only `Material.js` itself and `Moon.js`); the flag
  is inert for globe materials. Flipping it changed nothing (v4/v5/v6
  captures identical to v2).
- Instrumented live page: level-0 tiles stuck `renderable=false`,
  `_tilesToRender=0`, zero imagery errors — imagery requests hang, tiles
  never become renderable. Removing the material at runtime did not help.
- Repro matrix: imagery failing **fast** + material → globe renders base
  color (mean RGB ≈ pure blue); **working** local imagery + material + 300 m
  terrain → globe renders with the tint blended over imagery exactly per the
  GlobeFS `alphaBlend(materialColor, color)` math; OSM hanging 150 s →
  nothing renders (environment artifact, pre-existing stock behavior,
  unrelated to the repair).

Conclusion: no code regression was shipped; no follow-up PR was needed. The
deployed build renders correctly wherever imagery resolves (success or
failure), which includes the owner's real browser.
